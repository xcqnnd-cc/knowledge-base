# 题库数据中台内容治理、多端渲染与组卷打印一体化技术解决方案

## —— 面向“自建题库 + 学科网题源”的标准化供题平台

## 1. 项目背景

当前题库数据中台的核心职责，已经不只是“存题”和“维护题”，而是要成为统一的**题目供给平台**：

* 面向内部完成题库维护、修订、分类与审核；
* 面向下游系统提供稳定的推题能力；
* 面向多端支持 Web、小程序、后续 App / PDF / 打印等场景；
* 面向教学场景支持选题、组卷、预览、打印与下发。

现阶段题源主要包括两类：

1. **自建题库**
2. **学科网题源**

从产品与行业场景看，这条路线是成立的。学科网开放平台本身就提供组卷、备课、试题推送、章节/知识点推题等能力，并面向智慧校园、互动课堂、智能硬件、阅卷系统等场景输出服务；学科网主站也定位为面向 K12 的教学资源平台，提供试题、试卷、课件、教案等资源。也就是说，“题库中台作为内容供给层，再向其他业务系统推题”这件事，本身就有成熟的外部场景基础。

当前技术难点集中在内容形态上：

* 学科网返回内容以 **HTML 富文本**为主；
* 数学、物理、化学等学科经常包含**复杂 LaTeX 公式**；
* Web 前端直接 `v-html` 展示通常可行；
* 小程序当前看起来“也能显示”，但长期稳定性、跨端一致性和可治理性仍然存在明显风险。

因此，本项目真正要解决的问题不是“前端是否能显示”，而是：

> **如何把第三方复杂题目内容，沉淀为可治理、可搜索、可推送、可多端一致展示、可组卷打印的标准内容资产。**

---

## 2. 问题定义

如果只是从单页面展示角度看，原始 HTML 直接渲染似乎已经“能用”；
但这从中台视角看，直接展示并不等于已经形成解决方案。

### 2.1 多端一致性不可控

Web 能展示，不代表小程序、打印、PDF 导出、外部嵌入系统都能稳定一致。
尤其题目中如果包含：

* 复杂公式
* 表格
* 行内样式
* 图片与外链资源
* MathML / SVG
* 嵌套标签与特殊实体

不同终端对原始 HTML 的解析结果很容易出现差异。

### 2.2 内容治理能力不足

如果平台只存一份原始 HTML，那么后续很多能力都很难做好：

* 题干 / 选项 / 答案 / 解析拆分
* 搜索索引
* 知识点标注
* 相似题去重
* 内容巡检
* 公式统计
* 打印排版
* 多渠道输出

### 2.3 推题服务难以标准化

如果下游系统只能拿原始 HTML 自己适配，就会出现：

* Web 适配一套
* 小程序适配一套
* 打印适配一套
* 组卷适配一套
* 智能硬件适配一套

这样题库中台就没有真正成为“供题平台”，而只是“内容转运站”。

### 2.4 打印场景会放大问题

一旦题目进入“选题 → 组卷 → 打印”链路，问题会更加明显：

* 公式是否可打印
* 表格是否跨页错乱
* 图文题是否被截断
* 页眉、页脚、分值、答题区能否统一排版
* 浏览器打印与正式 PDF 是否一致

所以，这个项目必须从平台角度重新定义：

> **输入是第三方原始内容，输出必须是标准内容模型和多渠道渲染产物。**

---

## 3. 建设目标

本方案的目标不是单点修补，而是建设一套题库中台级能力。

### 3.1 核心目标

第一，**统一内容标准**
把学科网 HTML、自建题库内容统一进入标准化内容模型。

第二，**支持多端稳定展示**
支持 Web 管理端、Web 业务端、小程序、后续 PDF / 打印链路。

第三，**复杂公式稳定处理**
尤其面向数学、物理、化学等公式密集学科。

第四，**支持题目供给与推题**
向下游系统输出统一 API，而不是让各端自行解析题目内容。

第五，**支持选题组卷与打印**
形成“内容中台 → 组卷 → 打印输出”的完整闭环。

第六，**支持后续演进**
为搜索、推荐、个性化推题、错题重练、组卷系统等能力预留基础。

### 3.2 非目标

首期不追求：

* 一次性重做所有历史存量题；
* 所有终端像素级完全一致；
* 每个复杂长尾题型一步到位全部治理完成。

## 4. 外部技术调研结论

### 4.1 学科网场景侧结论

学科网开放平台明确提供试题推送、章节 / 知识点推题、组卷等服务，并面向智慧校园、互动课堂、智能硬件、阅卷系统等场景。这个事实说明，你们的题库数据中台如果承接“接题、管题、推题、组卷、打印”，在产品场景上是合理的，不是单纯内部技术自嗨。

### 4.2 公式渲染技术结论

#### KaTeX

KaTeX 官方将自己定义为面向 Web 的高速数学排版库，支持浏览器端 `render`，也支持服务端 `renderToString`；如果遇到不支持的 LaTeX 或非法输入，默认会抛出解析错误，也可以通过 `throwOnError: false` 降级处理；其文档同时强调，要正确输出服务端渲染结果，还需要 CSS 和字体资源配合。

#### MathJax

MathJax 官方文档说明，它支持 **LaTeX、MathML、AsciiMath** 输入，并可输出 **HTML+CSS、SVG、MathML**；同时自带较强的无障碍能力支持。这意味着对于复杂公式、兼容性要求更高的场景，MathJax 的覆盖面更强。

#### 结论

从平台视角，不建议二选一，而建议：

> **KaTeX 作为主渲染引擎，MathJax 作为复杂公式 fallback / 兜底引擎。**

理由不是“哪个更先进”，而是：
* KaTeX 更适合高频、轻量、性能优先场景；
* MathJax 更适合复杂语法、SVG 输出和高兼容场景。

### 4.3 小程序富文本结论

`mp-html` 是当前小程序侧常见的富文本组件方案之一。其官方 README 明确写到，它支持多个主流小程序平台和 uni-app，支持 `table`、`video`、`svg`、大部分 HTML 实体，并且支持 `latex` 公式插件。

但同时，社区 issue 也能看到 latex 相关边界问题，例如：
* 特定公式中 `&` 的处理与插件逻辑冲突；
* 某些公式排版和换行存在问题。

因此技术结论应当是：

> **小程序富文本可用，但不适合把“端上实时解析复杂公式”作为唯一方案。**

更稳妥的方式是：
* 富文本走小程序可控组件；
* 复杂公式优先走服务端预渲染产物。

## 5. 总体方案设计

本方案建议采用：

> **一份原始内容 + 一份标准内容模型 + 多份渠道渲染产物 + 一份打印产物** 的四层结构。

### 第一层：原始层 Raw

保留第三方原始内容，不做语义损失：
* 原始 HTML
* 原始 LaTeX 片段
* 原始图片链接
* 来源信息
* 来源题号
* 同步版本
* 同步时间

### 第二层：标准层 Canonical

把内容解析为平台自己的标准结构：
* 题干 / 选项 / 答案 / 解析
* 学科 / 学段 / 年级
* 题型 / 难度 / 知识点
* 图片节点
* 表格节点
* 公式节点
* 资源清单

### 第三层：渠道层 Render Artifacts

针对不同终端生成不同产物：
* `web_html`
* `mini_html`
* `plain_text`
* `search_text`
* `formula_assets`

### 第四层：打印层 Print Artifacts

针对试卷和纸质场景生成：
* `print_html`
* `print_pdf`
* `answer_pdf`
* `analysis_pdf`
* `print_snapshot`

这四层模型的关键意义在于：

> **原始内容只是输入，不再是平台唯一事实；标准模型才是平台事实；不同终端消费的都是标准模型派生产物。**

## 6. 总体技术架构

```text
内容来源（学科网 / 自建） 
        ↓ 
采集接入层 
        ↓ 
内容预处理层 
  - HTML 解析 
  - 白名单清洗 
  - 图片归档 
  - 公式识别 
  - 结构切片 
        ↓ 
标准内容模型层 
  - 题干 / 选项 / 答案 / 解析 
  - 公式节点 
  - 表格节点 
  - 元数据 
        ↓ 
渲染产物生成层 
  - Web 产物 
  - 小程序产物 
  - 公式 SVG / 图片产物 
  - 检索文本 
        ↓ 
内容供给层 
  - 题库维护 
  - 推题 API 
  - 搜索 / 推荐 
  - 内容预览 
        ↓ 
组卷打印层 
  - 选题 
  - 试卷结构化 
  - 打印模板 
  - PDF 生成 
        ↓ 
消费端 
  - Web 
  - 小程序 
  - 组卷系统 
  - 练习系统 
  - 阅卷系统 
  - 打印系统 
```

### 架构原则

第一，**前端不直接长期依赖第三方原始 HTML 作为唯一事实来源**。
第二，**复杂公式处理尽量前移到服务端**。
第三，**中台输出按渠道的渲染产物，而不是让每个业务端自己发明解析逻辑**。
第四，**打印视为独立渲染链路，不复用普通详情页 DOM**。

## 7. 内容接入与标准化方案

### 7.1 内容接入

输入来源包括：
* 学科网试题推送或相关题源接口；
* 自建题库内容；
* 历史存量迁移数据。

首要原则是：**原始内容先完整落库**，不要一边解析一边覆盖。

建议保留字段：
* `source_vendor`
* `source_question_id`
* `raw_html`
* `raw_answer`
* `raw_analysis`
* `source_version`
* `ingest_time`

### 7.2 HTML 解析与白名单清洗

服务端建立统一的内容预处理管线：

1. HTML 转 AST；
2. 去除危险标签、事件属性和不可控内联行为；
3. 统一图片、链接、表格等标签规则；
4. 对外链资源转内部代理或 CDN；
5. 提取题干、选项、答案、解析结构。

这里要明确一条工程原则：

> **HTML 清洗是中台能力，不应该下放到每个业务前端。**

### 7.3 公式识别与抽取

在预处理阶段统一识别：

* `\( ... \)`
* `\[ ... \]`
* `$...$`
* `$$...$$`
* 特定公式容器
* MathML
* 化学式 / 物理式等扩展写法

识别后形成独立公式节点，并保留：
* 原始公式文本
* 行内 / 块级模式
* 渲染状态
* fallback 状态
* 公式产物地址

### 7.4 标准内容模型

建议题目对象最少包含：
* 题目元信息
* 结构化内容
* 公式集合
* 资源集合
* 各渠道渲染产物
* 版本信息

核心思想是：

> **题目不再是一坨 HTML，而是一份结构化文档。**

## 8. 多端渲染方案

### 8.1 Web 端

Web 端分两类：

#### 管理端 / 运营端
目标是：
* 题目维护
* 内容审核
* 预览调试
* 渲染问题排查

建议展示三种视图：
* 原始内容视图
* 标准内容视图
* 最终渲染视图

这样便于定位是“来源问题”“解析问题”还是“渲染问题”。

#### 业务端 / 推题端
目标是：
* 高性能
* 一致性
* 稳定展示

建议直接消费中台生成的 `web_html`，而不是再吃原始 HTML。

### 8.2 公式 Web 渲染策略

建议：
* 普通公式：KaTeX
* 复杂公式：MathJax fallback
* 对高风险公式：生成 SVG 作为稳定产物

这样既能保留常规性能，也能覆盖复杂场景。KaTeX 支持服务端 `renderToString`，MathJax 支持 SVG 输出，这两点非常适合做中台预处理链路。

### 8.3 小程序端

小程序端建议采用“双模式”：

#### 模式 A：普通富文本 + 简单公式
* 使用中台输出的 `mini_html`
* 配合 `mp-html` 等组件处理普通富文本和轻量公式

#### 模式 B：复杂公式 / 高风险题
* 服务端提前生成 SVG 或高分辨率图片
* 小程序只负责展示，不承担复杂公式实时解析

这样做的理由很清楚：
* `mp-html` 能力足够承载普通场景；
* 但复杂 latex 问题在社区里已经出现，说明不能把端上解析作为唯一依赖。

#### 结论

> **小程序端以“中台预处理产物”为主，端侧解析为辅。**

## 9. 推题服务方案

题库中台既然要向其他系统供题，就不应只输出原始 HTML 字段，而应输出**标准供给接口**。

### 9.1 题目详情接口

输出：
* 题目元数据
* 标准内容结构
* 公式信息
* 按渠道渲染产物
* 版本信息

### 9.2 推题接口

支持输入：
* 学科
* 学段
* 年级
* 知识点
* 难度
* 题型
* 来源策略
* 渠道标识（web / mini / print）

输出：
* 题目列表
* 渲染产物
* 资源引用
* fallback 标记

### 9.3 预览接口

支持：
* Web 预览
* 小程序预览
* 打印预览
* 渲染调试

### 9.4 校验接口

输出：
* 是否存在未解析公式
* 是否存在风险标签
* 是否存在外链资源
* 是否命中公式 fallback

这一步的价值是，把供题能力真正标准化，而不是让下游系统各自适配。

## 10. 选题、组卷与打印一体化方案

打印不能被定义成“前端一个按钮”，而应该被定义成：

> **题库内容在纸质试卷场景下的一种专用渲染能力。**

### 10.1 业务流程

```text
题库检索 / 系统推题 
        ↓ 
教师 / 运营选择题目 
        ↓ 
组卷 
  - 排序 
  - 分组 
  - 设分值 
  - 配标题 
        ↓ 
生成试卷结构 JSON 
        ↓ 
内容中台拉取标准题目内容 
        ↓ 
打印渲染服务生成 print_html 
        ↓ 
公式 / 表格 / 图片打印态转换 
        ↓ 
PDF 服务输出正式打印稿 
        ↓ 
前端预览 / 下载 / 打印 / 留档 
```

### 10.2 为什么不能直接打印普通展示页

因为普通展示页的目标是“阅读和交互”，打印稿的目标是“版式和输出”。

打印场景必须额外处理：
* 页眉页脚
* 姓名班级栏
* 分值
* 大题结构
* 答题留白区
* 公式打印清晰度
* 图片和表格跨页
* 页码和模板

所以，打印必须走独立渲染链路。

### 10.3 试卷结构模型

组卷阶段不只是记录题目 ID，还要记录编排信息，例如：
* 题号顺序
* 所属大题
* 分值
* 是否显示答案
* 是否显示解析
* 是否允许分页前置
* 是否要求与下一题同页

也就是说，打印面对的对象不是“题目数组”，而是“试卷文档结构”。

### 10.4 打印技术路线

推荐：

> **选题 → 组卷结构化 → 生成打印 HTML → 服务端转 PDF / 浏览器打印**

其中：
* HTML 用于预览；
* PDF 用于正式输出；
* 浏览器打印作为轻量补充，而不是唯一正式方案。

### 10.5 打印中的公式策略

打印场景中，复杂公式建议优先走：
* 服务端预渲染 SVG
* 极端复杂场景下转高分辨率图片兜底

这样原因很直接：
* 跨浏览器更稳
* PDF 更一致
* 打印清晰度更可控

#### 推荐结论

> **屏幕端以公式文本渲染为主，打印端以预渲染产物为主。**

### 10.6 打印中的图片与表格

图片必须提前：
* 转内部资源
* 获取宽高
* 统一清晰度与宽度规则

表格必须作为高风险节点单独治理：
* 宽表格做打印态宽度适配
* 长表格避免随意断页
* 必要时允许整块图片化兜底

### 10.7 打印输出形式

建议采用双轨制：
* **后台预览**：打印专用 HTML
* **正式输出**：服务端 PDF

这样兼顾预览效率和正式交付稳定性。

## 11. 搜索、检索与后续智能化能力

既然题目已经标准化，中台就可以顺便形成检索基础能力。

建议在预处理阶段同步生成：
* `plain_text`
* `search_text`
* 公式文本表达
* 知识点标签
* 题型标签
* 难度标签
* 来源标签
* 公式复杂度标签

这一步的价值在于，题库中台未来可以自然演进到：
* 搜索
* 组卷筛题
* 相似题推荐
* 错题补弱
* 个性化推题
* 使用反馈回流

## 12. 安全、治理与质量控制

### 12.1 安全

所有 HTML 必须在中台做白名单治理，不能将第三方原始 HTML 直接作为各业务端展示的长期方案。

### 12.2 来源治理

保留来源信息：
* 来源平台
* 来源题号
* 来源版本
* 同步时间
* 授权范围标记

### 12.3 版本治理

内容应有三类版本：
* 原始版本
* 标准版本
* 渲染版本

这样渲染问题、公式问题、资源问题才可追踪。

### 12.4 质量治理

建议建立内容质量指标，例如：
* HTML 清洗成功率
* 结构切片成功率
* 公式可渲染率
* fallback 比例
* 图片可用率
* 打印成功率

这样中台才能从“内容存储”升级成“内容治理平台”。

## 14. 风险与应对

### 风险 1：学科网返回内容形态复杂
应对：
* 原始内容完整保留；
* 解析失败可回退；
* 按学科逐步沉淀规则。

### 风险 2：复杂公式在小程序侧不稳定
应对：
* 中台预渲染 SVG；
* 小程序复杂公式优先展示产物，不强依赖端侧解析。

### 风险 3：打印排版难度高
应对：
* 打印独立渲染；
* PDF 正式输出；
* 图表公式打印态前移处理。

### 风险 4：各业务系统接入不一致
应对：
* 中台统一输出按渠道产物；
* 禁止各端长期直接消费原始 HTML。

## 15. 最终建议

这件事不应继续定义为：

> “学科网返回 HTML，Web 和小程序看起来能显示，所以先这样用。”

更合理的定义应该是：

> **建设一套面向题库中台的“内容标准化 + 多端渲染 + 推题供给 + 组卷打印”一体化能力。**

### 最终技术建议

在内容层：
* 保留原始内容；
* 建设标准内容模型；
* 生成渠道化渲染产物；
* 增加打印产物层。

在公式层：
* Web 端：KaTeX 主渲染，MathJax 兜底；
* 小程序端：轻量公式可端渲染，复杂公式优先服务端 SVG / 图片产物；

在供题层：
* 下游消费标准 API；
* 不让每个系统自己解析原始题目。

在打印层：
* 选题 → 组卷结构化 → 打印专用 HTML → PDF；
* 打印视为独立产物，不直接复用业务详情页。

---

## 16. 一句话总结

这不是一个“HTML 怎么显示”的问题，而是一个更大的平台问题：

> **如何把来自学科网和自建题库的复杂题目内容，沉淀为可治理、可搜索、可推送、可多端稳定展示、可组卷打印输出的标准内容资产。**
